## ATS OPTIMIZATION RULES

### Must Follow:

1. **Use Standard Section Headings**

   - PROFESSIONAL SUMMARY (not "About Me" or "Profile")
   - TECHNICAL SKILLS (not "Core Competencies")
   - EXPERIENCE (not "Work History" or "Employment")
   - EDUCATION (not "Academic Background")
   - PROJECTS (not "Portfolio")

2. **Avoid These Elements**

   - Tables for main content (ATS can't parse)
   - Images, icons, or graphics in content
   - Headers/footers with critical info
   - Text boxes or columns that break reading order
   - Special characters (use standard ASCII)

3. **Keyword Optimization**

   - Include keywords that match the job description AND exist in the user's skill files
   - Use both spelled-out terms AND acronyms (e.g., "Application Programming Interface (API)")
   - Place important keywords in first 1/3 of resume
   - Include skills in both Skills section AND in experience bullet points

4. **File Format**
   - PDF is preferred for most applications
   - Ensure PDF is text-based, not image-based
   - Use standard fonts (Inter, Arial, Calibri, Times New Roman)

## SKILL VALIDATION RULES

**This section is NON-NEGOTIABLE. Violations here produce a dishonest resume.**

1. **ONLY use skills that exist in `resources/skills.json` or `resources/additional-skills.json`.**
   These files contain the user's verified, real skills. They are the single source of truth.

2. **If a job description requires a skill NOT found in those files:**
   - STOP. Do NOT add it to the resume.
   - ASK the user: "The job requires [skill X]. I don't see it in your skills files. Do you have this skill?"
   - Wait for the user's response before proceeding.
   - This applies to EVERY missing skill, no matter how minor.

3. **If the user confirms they have the skill:**
   - Add it to the appropriate category in `resources/skills.json` first.
   - Then include it on the resume.

4. **If the user says they don't have the skill:**
   - Do NOT include it on the resume. Period.
   - Find the closest related skill the user DOES have and emphasize that instead.

5. **Variant matching is allowed.** The skills files include a `variants` field.
   - If the job says "React" and skills.json has "React.js" with variant "React", that's a match.
   - If the job says "Postgres" and skills.json has "PostgreSQL", that's a match.
   - Use the job description's exact phrasing when a variant match exists.

6. **When reordering skills for a specific job:**
   - Only reorder existing skills. Never add new ones without user approval.
   - Put the most job-relevant skills first in each category.

## CONTENT SOURCING RULES

**All resume content must come from the user's own files. Never fabricate or copy from job descriptions.**

### Where to source content:

| Content Type | Source Files |
|---|---|
| Skills | `resources/skills.json`, `resources/additional-skills.json` |
| Experience bullets | `resources/experience.json`, `docs/full-experience.md` |
| Metrics & numbers | `docs/achievements.md`, `resources/experience.json` |
| Project details | `resources/projects.json`, `docs/projects-detail.md` |
| Personal info | `resources/profile.json` |

### What you MUST NOT do:

1. **Do NOT copy phrases from the job description.** The resume should sound like the user wrote it, not like the job posting was rearranged. Recruiters notice when resume language mirrors their posting verbatim.

2. **Do NOT fabricate metrics.** Only use numbers that appear in the source files (e.g., "15% load time improvement", "500+ concurrent users", "5+ production apps"). If you need a metric and can't find one, write the bullet without a number.

3. **Do NOT invent experience.** Every bullet point must trace back to something in `experience.json` or `docs/full-experience.md`. You may rephrase for clarity and relevance, but the core claim must be real.

### What you CAN do:

1. **Rephrase and adapt** existing bullets to emphasize relevance to the target job. Change emphasis, not facts.

2. **Combine** related achievements from the source files into a single concise bullet.

3. **Select** the most relevant bullets from a larger set — you don't need to use all of them.

4. **Use action verbs** (Built, Developed, Implemented, etc.) to strengthen existing content.

### Professional Summary:

1. 3-4 sentences maximum
2. Start with job title + years of experience (based on actual dates in experience.json)
3. Include 2-3 key specializations (from the user's actual work)
4. Mention 3-4 core technologies (from skills.json)
5. End with value proposition (based on achievements.md)
6. Tailor emphasis to the target job, but every claim must be sourced

### Experience Bullet Points:

1. **Follow CAR format (Challenge, Action, Result):**
   - Bad: "Worked on React applications"
   - Good: "Built 5+ React applications serving 10K+ daily users, reducing load time by 40%"

2. **Start with strong action verbs:**
   Built, Developed, Implemented, Designed, Led, Optimized, Integrated, Architected, Deployed, Created

3. **Include metrics from source files when available**

4. **Maximum 4 bullets per role**

5. **Use present tense for current role, past tense for previous**

### Skills Section:

1. Group by category (matching categories in skills.json)
2. List most relevant skills first (reorder only, never add)
3. Don't include soft skills (show them through experience bullets)
4. Maximum 6-8 categories

### Projects:

1. Include project name as heading
2. 2-3 bullet points per project (sourced from projects.json / projects-detail.md)
3. Emphasize technologies and outcomes
4. Include links if available (GitHub, live demo)

## FORMATTING & LAYOUT RULES

### WYSIWYG — Browser = PDF

The HTML view and PDF output use **identical styles**. There are NO separate print font sizes or spacing. What you see in the browser is exactly what prints to PDF. Do not add or suggest `@media print` size overrides.

### Spacing:

```
Section margin-bottom: 6px
Experience/project item margin-bottom: 6px (last child: 0)
List item margin-bottom: 1px
Section title padding-bottom: 2px
Section title margin-bottom: 5px
```

### Typography:

```
Name: 28pt, font-weight-700, letter-spacing 1px, uppercase (Bricolage Grotesque)
Section Titles: 10pt, font-weight-700, letter-spacing 1.5px, uppercase (Inter)
Body Text: 9.5pt, line-height 1.45 (Inter)
Contact/Links: 10pt, line-height 1.6
Experience Title: 10.5pt
Experience Date: 10pt
Skills List: 9.5pt, line-height 1.4
Resume List: 9.5pt, line-height 1.4
```

### Alignment:

```
Header: text-center
Experience Headers: flex justify-between items-baseline
  - Left: Company | Role
  - Right: Date (whitespace-nowrap)
Lists: margin-left 14px, list-disc
```

### Colors:

```
Name/headings/strong: #000000
Body text: #333333
Links: #2563eb
Section borders: #000000
```

### Page Container:

```
Width: 8.5in
Height: 11in (max-height: 11in)
Padding: 0.3in top/bottom, 0.4in left/right
Overflow: hidden (content cut off if too long)
```

## PAGE CONSTRAINTS

**RESUME MUST ALWAYS BE EXACTLY ONE PAGE — NON-NEGOTIABLE**

### Validation (REQUIRED after every edit):

After editing `index.html`, you MUST run the validation script:

```bash
node validate-page.js
```

This script measures the actual rendered height of the resume using Puppeteer. It will report:
- **PASS**: Content fits within 11 inches
- **FAIL**: Content overflows, with details on how much and which sections are large

**Do NOT rely on visual estimation or character counting.** Always run the script.

### PDF Generation (REQUIRED — do NOT use window.print()):

```bash
node generate-pdf.js              # outputs resume.pdf
node generate-pdf.js my-resume.pdf  # custom filename
```

This generates a pixel-perfect PDF using Puppeteer. Do NOT use the browser's print dialog — it renders differently and can clip content.

### If validation fails, reduce content in this order:

1. Reduce project bullet points (1 per project minimum)
2. Reduce experience bullets to 3 per role
3. Shorten professional summary to 3 sentences
4. Remove least-relevant project
5. Remove least-relevant experience role (keep minimum 2)

### Before asking the user, try to fix overflow yourself by reducing content. Only ask the user if you need to make a judgment call about what to remove.

### Content budget guidelines (approximate):

- Total sections: 5-6 max (Summary, Skills, Experience, Education, Projects)
- Experience bullets: 3-4 per role maximum
- Project bullets: 1-2 per project maximum
- Summary: 3-4 sentences maximum

## TECHNICAL IMPLEMENTATION RULES

### HTML Structure:

```html
<section class="resume-section">
  <h2 class="section-title">SECTION TITLE</h2>
  <div>
    <!-- Content -->
  </div>
</section>
```

### Experience Item Structure:

```html
<div class="experience-item">
  <div class="experience-header">
    <span class="experience-title"><strong>Company</strong> | Role</span>
    <span class="experience-date">Date</span>
  </div>
  <ul class="resume-list">
    <li>Bullet point</li>
  </ul>
</div>
```

### Skills Row Structure:

```html
<div class="skills-list">
  <p><strong>Category:</strong> Skill1, Skill2, Skill3</p>
</div>
```

### Project Item Structure:

```html
<div class="project-item">
  <p class="project-title">

  </p>
  <ul class="resume-list">
    <li>Bullet point</li>
  </ul>
</div>
```

## TAILORING FOR JOBS

### Step-by-step process:

1. **Read the job description** from `jobs/` folder

2. **Read the user's skill files:**
   - `resources/skills.json`
   - `resources/additional-skills.json`

3. **Identify skill gaps** — list every job requirement NOT in the skill files.
   Present them to the user:
   > "The job description mentions these skills I don't find in your files:
   > - **Kubernetes** — not in skills.json
   > - **GraphQL** — not in skills.json
   >
   > Do you have experience with any of these?"

   Wait for the user's response before continuing.

4. **Read experience and achievement files:**
   - `resources/experience.json`
   - `docs/full-experience.md`
   - `docs/achievements.md`
   - `resources/projects.json`
   - `docs/projects-detail.md`

5. **Select relevant content** from resource files:
   - Pick experience bullets that relate to the job requirements
   - Choose projects that demonstrate relevant skills
   - Select metrics that show impact in relevant areas

6. **Draft the resume** by adapting selected content:
   - Professional Summary — emphasize relevant specializations
   - Skills section — reorder to match job priorities (only existing skills)
   - Experience bullets — select and adapt relevant bullets from source files
   - Projects — highlight most relevant ones

7. **Edit `index.html`**

8. **Run validation:**
   ```bash
   node validate-page.js
   ```

9. **If validation fails**, reduce content and re-validate

10. **Generate PDF:**
    ```bash
    node generate-pdf.js
    ```

11. **Report to user:**
    - Which skills were included
    - Which experiences were highlighted
    - Validation result (PASS/FAIL)

### Keyword matching rules:

- If the job says "React" and you have "React.js" in skills.json → use "React" on the resume (variant match)
- If the job says "CI/CD" and it's in skills.json → include it
- If the job says a skill you don't have → ASK, don't add
- Use the user's own words from their resource files, NOT the job description's phrasing

## INTERACTIVE WORKFLOW

The AI must pause and ask the user in these situations:

### 1. Missing Skills (ALWAYS ask)

When ANY skill in the job description is not found in `resources/skills.json` or `resources/additional-skills.json`:

> "The job requires these skills not in your files:
> - [Skill 1]
> - [Skill 2]
>
> Do you have experience with any of these? I'll add confirmed skills to your files."

### 2. Content Overflow (ask if judgment needed)

If the resume overflows and you're unsure what to cut:

> "The resume exceeds one page by [X inches]. I suggest removing:
> - [Specific content to remove]
>
> Should I proceed?"

### 3. Ambiguous Relevance (ask when unclear)

When the job could match multiple experiences or projects equally well:

> "The job emphasizes [domain]. Which experience is most relevant to highlight:
> - [Option A]
> - [Option B]?"

### 4. Role Title Mismatch

When the user's actual role title differs significantly from the job's title:

> "Your role at [Company] was '[Actual Title]'. The job is for '[Job Title]'. Should I keep your actual title or adjust the professional summary wording?"
